# IWP 翻译诊断报告（2026-11-22 17:24，插件 2.0.11）

## 一、多路翻译速度慢的根本原因

### 结论：宿主 HTTP 门面把并发请求串行化了，三路实际是单路

**硬证据（llama-server 请求时间线分析）：**

| 指标 | 实测值 | 应有值 |
| --- | --- | --- |
| 峰值并行度（同时在推理的请求数） | **1** | 3 |
| 双请求重叠事件数 | **0** | 大量 |
| 请求模式 | S→E→S→E 严格串行，间隔约 60ms | 应 3 个 S 连续 |
| slot 请求分布 | 255/255/255（均衡） | — |
| GPU 利用率 | 37% | 应接近满载 |

slot 均衡说明上轮的 LCP 选槽修复生效；但**请求在服务端严格排队**，同一时刻只有一个在跑。continuous batching 默认开启、服务端具备并发能力（历史日志佐证），所以瓶颈不在引擎。

**根因定位（版本对照）：**

| 日志时间 | 插件版本 | HTTP 路径 | 峰值并行度 |
| --- | --- | --- | ---: |
| 11-16 20:40 | 2.0.4 | 自建 `_http_request`（urllib） | **2** |
| 11-20 21:45 | 2.0.5+ | 宿主门面 `api.host.http_post` | **1** |
| 11-22 17:13 | 2.0.11 | 宿主门面 | **1** |

2.0.5 按平台作者要求"跟随宿主、去除二次实现"，把翻译请求从自建 urllib 切到 `api.host.http_post`。宿主的门面内部大概率封送到 UI 线程或以全局锁执行，导致 3 个 worker 的请求被串行化。日志中门面失败仅 1 条（启动健康检查），说明翻译期门面**持续成功**——即每个翻译请求都走了这条串行通道。

这也解释了上轮修复的悖论：slot 从"slot2 独占 1621 次"变成"255/255/255 均衡"，但吞吐纹丝不动——因为请求本来就是一个一个来的，分给哪个 slot 都无所谓。

**修复方向（二选一）：**

1. **翻译请求走自建 urllib**（推荐）：在 `_http_post` 增加"大并发小文本"分支——翻译/会话词表这类高频请求直接 `_http_request`，只有零散小请求走门面。可恢复 2.0.4 的并行度。代价：与"跟随宿主"要求有偏离，需平台作者确认门面是否可并发调用。
2. **让平台作者修门面**：确认 `api.host.http_post` 能否从工作线程并发调用；若不能，请其提供线程安全版本。这是最干净的方案，但依赖上游。

验证方法：改完后重跑，检查 server 日志峰值并行度应回到 ≥2，吞吐应接近翻倍。
